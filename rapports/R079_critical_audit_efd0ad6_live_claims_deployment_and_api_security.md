## Executive conclusion

**The commit contains useful progress, but it does not establish that the public demo is safe for unrestricted production use or that every reported attack run is generated by a live LLM.** The strongest concerns are synchronous voice synthesis inside the SSE execution path, public unauthenticated execution endpoints, personal-data-bearing GET parameters, and deployment automation that disables SSH host-key verification.

This audit distinguishes source-code findings from operational claims recorded in R067–R078. A report saying that a request succeeded is not independent proof that the service remains healthy now.

## Findings by priority

### P0-1 — Voice synthesis still blocks later SSE pipeline steps

**Evidence:** In `guardian_api/app.py`, `_sse_generator()` emits `session_opened` and then immediately calls `yield from _emit_voice(...)`. The helper emits `voice_script`, then invokes `vc.speak_commentator()` or `vc.speak_agent()` synchronously before returning control to the generator. The same pattern follows later events.

**Process — what happens:** A generator yields an SSE event to the client, then continues executing. When the generator calls a synchronous voice provider, it cannot advance to the next pipeline stage until that call returns.

**Problem — why it matters:** Emitting `guardian_decision` before that step's narration protects the ordering of that one event, but it does **not** prove that voice latency never delays the overall pipeline. Earlier narration can delay LLM attack generation, propagation, and subsequent events. A slow provider or timeout can therefore stall the stream and increase end-to-end latency.

**Correction:**
1. Move all speech generation to a separate bounded worker/queue.
2. Emit security decisions and chain-verification events without awaiting voice work.
3. Add explicit timeouts, cancellation, queue limits, and metrics for dropped/late audio.
4. Add a regression test with a deliberately blocked TTS provider; assert that security events and the final decision still arrive within the defined latency budget.

**Acceptance test:** With TTS blocked indefinitely in a test double, the security pipeline must still complete and emit its security events; only audio delivery may be delayed or omitted.

### P0-2 — Public execution endpoints have no visible authentication or rate limiting

**Evidence:** The reviewed routes include `POST /api/simulation/run`, `POST /api/llm-attack/run`, and `POST /api/llm-attack/stream`. The latter two check `GUARDIAN_ATTACKER_ENABLED`, but the reviewed route code does not show caller authentication, authorization, per-client quotas, or rate limiting. The application configures CORS with `allow_origins=["*"]` (with credentials disabled).

**Process:** Any network client able to reach the published endpoint can attempt to trigger a simulation or LLM/SSE run while the feature flag is enabled.

**Problem:** An enabled feature flag is not caller authentication. Public callers may consume provider credits, CPU, memory, worker capacity, and long-lived SSE connections. CORS is a browser policy, not an API access-control mechanism.

**Correction:**
1. Put execution endpoints behind authenticated authorization (for example, short-lived signed tokens or an established identity gateway).
2. Apply per-identity and per-IP rate limits, concurrency caps, request timeouts, and maximum stream duration.
3. Keep health checks separately accessible if required, without exposing expensive actions.
4. Restrict CORS to the actual frontend origins; do not treat this as a replacement for authentication.
5. Add abuse tests that prove unauthenticated requests are rejected and that quotas remain effective under parallel requests.

**Status:** High-confidence source finding. Actual internet reachability and current proxy configuration were not retested during this audit.

### P0-3 — KYC identifiers are placed in GET query strings

**Evidence:** `start_guardian.sh` runs a demo request to `/api/kyc/stream` with fields such as `first_name`, `last_name`, `doc_id`, and `dob` in the URL query string. R078 also records that KYC data in URLs was already identified and remains to be corrected before real-data use.

**Process:** URLs are routinely captured by reverse-proxy access logs, application logs, browser history, monitoring systems, and intermediary tooling.

**Problem:** Names, document identifiers, and dates of birth can be copied into multiple systems beyond the intended KYC processor. HTTPS does not prevent the URL from being logged at the endpoints.

**Correction:**
1. Do not put personal or identity-document data in GET URLs.
2. Use a POST request with a validated JSON body or an appropriately protected request body for the streaming workflow.
3. Redact sensitive fields in access logs and tracing; never record raw identity payloads by default.
4. Use synthetic data in demonstrations and document retention/deletion rules.
5. Add tests that inspect access logs and telemetry to ensure these fields do not appear.

**Status:** The demo script demonstrates the risky pattern. Production exposure of real personal data is not established by this code review.

### P1-1 — The deterministic fallback can be mistaken for a live LLM attack

**Evidence:** `guardian_mcp/llm_attacker.py` catches any exception from the OpenAI call and returns a fixed tool call to `wallet.sign`, with destination `simulated-attack.invalid`, amount `100`, model `deterministic-fallback-v1`, and backend `fallback`. If no API key is configured, the same fixed fallback is returned. The module's introductory documentation still describes AWS Bedrock as the fallback, which no longer matches the inspected implementation.

**Process:** The demo pipeline can continue when a provider is unavailable by creating a deterministic simulated attack.

**Problem:** This is useful for availability, but it is not evidence that a live model generated the attack. A successful SSE run or a populated `attack_generated` event alone cannot establish live-LLM execution. Stale module documentation adds ambiguity.

**Correction:**
1. Preserve the explicit backend/model fields in every event and final result.
2. Label the run visibly as `LIVE_LLM`, `DETERMINISTIC_FALLBACK`, or `SIMULATION`.
3. For a competition or acceptance test claiming a live LLM, fail closed when the provider is unavailable rather than silently substituting a fixed action.
4. Update module documentation and tests to match the current fallback behaviour.
5. Keep provider failures and fallback transitions as structured, redacted audit events.

**Acceptance test:** A test without provider credentials must report `DETERMINISTIC_FALLBACK`; a live-LLM acceptance test must fail unless a real provider response and its request metadata are recorded.

### P1-2 — SSH host-key checking is explicitly disabled by the deployment script

**Evidence:** `deploy_terminator_ovh2.sh` passes `StrictHostKeyChecking=no` to its SCP and SSH commands.

**Process:** SSH host-key verification lets the client confirm that it is connecting to the expected server, rather than a machine impersonating it.

**Problem:** Disabling verification weakens protection against a man-in-the-middle or wrong-host deployment. The script also expects a private key at `/tmp/artcb_ssh/ovh2_key`; a temporary directory is not an ideal long-term location for a deployment credential.

**Correction:**
1. Pin and verify the expected host key using a managed `known_hosts` file.
2. Remove `StrictHostKeyChecking=no`; fail closed when host identity cannot be verified.
3. Store deployment credentials in a protected secret/credential mechanism with least-necessary scope, not a casually reused temporary path.
4. Use a dedicated deployment identity and audit the exact target host before copying files.
5. Test the deployment against a deliberately mismatched host key and confirm that it stops before any copy or remote command.

### P1-3 — The deployment script is not reproducible and does not itself configure HTTPS

**Evidence:** `deploy_terminator_ovh2.sh` hardcodes macOS-specific local paths such as `/Users/deyi/.bob/artcb_TERMINATOR_FRONTEND/index.html` and `/Users/deyi/.bob/terminator_repo`. The Nginx configuration written by this script contains a port-80 server block and no TLS listener or certificate configuration. It runs `nginx -t` only after writing the configuration and then reloads Nginx.

**Process:** The script copies local artifacts to a remote host, writes a server configuration, validates Nginx syntax, and reloads the service.

**Problem:** It is coupled to one workstation layout and cannot by itself establish the HTTPS behaviour claimed in the reports. Existing Nginx configuration may provide TLS, but that must be inspected and tested independently. Writing before validating a staged candidate also increases recovery risk if the resulting configuration is invalid.

**Correction:**
1. Make artifact paths configurable and validate every required input before connecting.
2. Render configuration to a temporary file, run `nginx -t` against the candidate configuration, then install atomically and reload.
3. Back up the current configuration and define rollback steps.
4. Verify TLS certificate chain, hostname, redirect behaviour, and API proxy paths in a separate post-deployment acceptance test.
5. Ensure the script's success message distinguishes “files copied” from “service and public HTTPS verified.”

### P1-4 — The R0 chain result is narrower than a global provenance guarantee

**Evidence:** The reviewed `/api/llm-attack/run` path computes hashes and parent links over the event list returned by the in-process defender, starting from `GENESIS_HASH`. The result is a useful check of that event sequence, but this code path alone does not demonstrate a durable, globally complete ledger covering every agent, external call, deployment action, or remote system.

**Process:** Each event's computed hash is compared with its stored hash and its previous-event reference.

**Problem:** A passing check means the inspected sequence satisfies the implemented checks at that moment. It does not by itself prove completeness, durable persistence, trusted timestamping, external-agent coverage, or protection against an attacker who can rewrite the entire in-memory sequence before verification.

**Correction:**
1. Label the result precisely (for example, “in-memory R0 hash/parent-link check”).
2. Persist events to the designated durable ledger before reporting durable verification.
3. Verify the stored sequence independently and include explicit coverage boundaries.
4. Test mutation, deletion, reordering, truncation, missing-event, and whole-sequence replacement cases.
5. Do not use a local R0 PASS as evidence of global or total system integrity.

## Recommended remediation order

1. **Immediately:** disable or protect public expensive execution routes until authentication, rate limits, and concurrency limits are in place.
2. **Immediately:** replace GET query-string KYC inputs with a protected POST workflow and remove personal data from URLs.
3. **Next:** decouple voice synthesis from the security execution path and add the blocked-TTS regression test.
4. **Next:** distinguish live LLM runs from deterministic fallback in API responses, UI, and reports.
5. **Before further deployment:** restore SSH host-key verification and make deployment validation staged and rollback-capable.
6. **Before claiming full provenance:** document R0 coverage boundaries and test the durable ledger independently.
